1. 项目定位与技术架构

一句话定位：给家庭/小班场景用的自托管 AI 错题本。拍照或截图 → 视觉大模型识别题目并给出答案、解析、错因、知识点标签 → 人工校对后归档 → 复习、练习、导出打印。它不是"拍照搜题"，而是"错题资产化"：把一次性作业错误沉淀成可检索、可统计、可打印的复习材料。

技术栈

框架Next.js 16（App Router）+ React 19
数据Prisma 5.22 + SQLite（better-sqlite3）
UITailwind CSS v4 + Shadcn/Radix + lucide
AIGemini / OpenAI(兼容) / Azure OpenAI，三实现统一接口
认证NextAuth v4（Credentials + JWT + Prisma Adapter）
测试Vitest（unit 20 + integration 13）+ Playwright（3 spec）

部署形态

镜像ghcr.io/wttwins/wrong-notebook，多架构构建
持久化./data（SQLite）+ ./config（运行时配置 JSON）
HTTPS内置 https-server.js（443→3000 反代，为截图功能提供安全上下文）
PWAapp/manifest.ts，可添加到手机主屏
网络global-proxy.ts 支持 HTTP(S)_PROXY 全局代理

核心数据流：upload-zone / image-cropper（截图或选图，canvas 降质压缩到 ≤1MB / ≤1920px）→ POST /api/analyze（先按用户学段+入学年份推算年级，再按错题本名推断学科，动态拼装受限标签词表注入 prompt）→ 视觉大模型返回结构化 JSON（Zod 校验 + jsonrepair 容错 + 重试）→ correction-editor 人工校对 → POST /api/error-items 落库。

3. 做得好的地方（值得学习借鉴）

① 标签收敛策略很专业

大模型打标最大的坑是"每次生成新标签，越用越乱"。本项目用教材标签树 + prompt 约束 + 启发式映射三件套把输出锁进可控集合，这是同类产品里少见的正解。

② 上下文感知的 prompt 组装

年级和学科不是让模型猜，而是由服务端从用户档案 + 错题本名推算后注入，等于给 VLM 加了先验，准确率与标签命中率都受益。

③ 三 Provider 统一抽象

analyzeImage / generateSimilarQuestion / reanswerQuestion / analyzeForGeoGebra 四方法接口 + 运行时配置热切换，加 Zod schema 校验 + jsonrepair + 重试，工程上很稳。

④ 自托管友好度

Docker 一键起、SQLite 单文件、代理支持、内置 HTTPS、PWA、前端日志回传、配置热更新——NAS/家庭服务器场景该踩的坑基本都考虑到了。

⑤ 人工校对位留得对

AI 结果先进 correction-editor 让用户改题面/答案/解析/标签再入本，而不是盲信直落库——教育类产品里这个"人在环上"的设计很关键。

⑥ 工程基线不差

TS strict 开启、结构化日志、统一错误码、CI（unit→integration→build→e2e→多架构镜像）、42 个测试文件、server/client 边界基本清晰。

4. 问题清单

4.1 安全（最需要优先处理）

结论先行：这个项目默认按"家庭内网可信环境"设计——一旦暴露到公网，下面几条高危项的组合（匿名可读配置 + 匿名可改配置 + SSRF + 弱口令 + 中间件 fail-open）足以被完全接管。
级别位置问题
高api/settings/route.ts:11-50GET/POST 均无鉴权。注释写着"authenticated endpoint"但代码里没有任何会话校验 → 匿名可读明文 API Key，匿名可改写 AI 配置与 baseUrl
高api/ai/models/route.ts:68-90无鉴权；apiKey/baseUrl 走 URL query → 密钥落进反代访问日志；同时是匿名 SSRF 代理
高middleware.ts:56-59getToken 抛错（NEXTAUTH_SECRET 缺失/不符）后 return next()——fail-open，认证失败即放行
高middleware.ts:71matcher 显式排除 api，/api/** 完全不受中间件保护，只能靠每个 route 自查（上面两条就是漏网的）
高prisma/seed.ts:6、docker-entrypoint.sh:54硬编码 admin@localhost / 123456，且每次容器启动都执行 seed、从不重置也不强制改密，无首次登录引导
高lib/config.ts:14,181baseUrl 用户可任意填且无白名单（SSRF 到 169.254.169.254 / 内网）；API Key 明文写 config/app-config.json，docker-compose 明文挂载
中api/error-items/[id]/notes/route.ts:28唯一漏掉的 IDOR：update({where:{id}}) 不带 userId → 任意登录用户可改他人错题备注（同类路由都校验了，属遗漏）
中api/tags/stats/route.ts:14无鉴权 + 全表 findMany → 跨租户泄露全部用户标签
中api/logs/frontend/route.ts:28-45无鉴权，任意内容可灌进服务端日志（日志投毒）
中api/register/route.ts注册默认开放，无邮箱验证/验证码，全项目找不到任何限流 → 批量注册刷库
中api/openclaw/batch-upload:261"用户不存在"返回 404 vs "密码错误"返回 401 → 用户名枚举 + 无限流可爆破
中lib/logger.ts全文无字段脱敏，logger.error({error}) 会序列化整个错误对象，AI 异常常带完整 request URL/headers（含 key）
中上传校验validateImage 只看文件名后缀，不校验内容；mimeType 直接取自请求体；/api/analyze 无大小上限；base64 图片直存 DB（5MB×20 直灌 SQLite）
低依赖next-auth 4.24.13（v4 末代维护版）；@prisma/client 5.22.0 与 @prisma/adapter-better-sqlite3 ^7.0.1 主版本不匹配且该 adapter 无人引用（冗余依赖）
低XSSreact-markdown 未挂 rehype-raw，全项目无 dangerouslySetInnerHTML，攻击面小 ✅

已核验：/api/ 下共 9 个路由完全没有鉴权调用（ai/models、logs/frontend、register、register/status、settings、tags/stats、version、openclaw/batch-upload 以及 auth 本身）。

4.2 工程质量与技术债

  • 巨型组件：settings-dialog.tsx 1544 行，把六个 Tab 的表单、校验、UI 全塞一起；translations.ts 1299 行、prompts.ts 665 行、app/page.tsx 619 行。
  • 重复的鉴权样板：getServerSession → findUnique(email) → user 三段式在十余个 route 里复制粘贴，缺少统一 getCurrentUser() 抽象——也正是这种重复导致了 notes 路由漏校验。
  • console.* 99 处、any / as any / @ts-ignore 109 处；错误处理有两套（api-errors.ts 与手写 {message} 并存），返回格式不统一。
  • 测试名不副实：13 个"integration"测试全部 mock 掉 @/lib/prisma 和 @/lib/config，从不连真实库，本质是带 handler 的单测；vitest.config.ts environment 是 jsdom，API 测试跑在浏览器环境。e2e 只有 3 个 spec，其中上传流程把 /api/analyze 也 mock 了，真实 AI 链路零覆盖。无覆盖率门禁，CI 不跑 lint、不跑 npm audit。
  • 迁移历史混乱：prisma/migrations 10 个目录里 3 个都叫 init（20251127 / 20251129 / 20251130），还出现 20260427、20260608 未来时间戳，无法线性重放。
  • 无健康检查接口、Dockerfile 无 HEALTHCHECK；docker-entrypoint.sh:47 迁移/seed 失败仅 || echo 静默吞错。

4.3 数据层

  • ErrorItem 缺 @@index([userId])（对比 KnowledgeTag 有）——而几乎全部查询都以 userId 过滤，数据量上来必然全表扫描。
  • N+1：error-items/list/route.ts:272 的 findChapterDescendantTagIds 用 while 循环逐层 findMany，标签树越深查询越多。
  • SQLite 未启用 WAL / busy_timeout；备份用 cp 直接拷库文件而非 .backup，热拷贝有损坏风险。

4.4 产品断层（功能"看起来有，实际没通"）

项实际情况
间隔复习（ReviewSchedule）完全空转。整个模型只在导入导出里被搬运；lib/scheduler.ts 的艾宾浩斯算法零引用（死代码），scheduledFor/completedAt/isCorrect 无任何写入与 UI。这是错题本最核心的留存价值，等于没做
练习记录（PracticeRecord）只写 subject/difficulty/isCorrect，未关联 errorItemId → 无法回溯练的是哪道题、无法按错题聚合

5. 改进方向（按优先级）

P0 · 安全底线（不做完不建议暴露公网）

  1. 给 /api/settings、/api/ai/models、/api/tags/stats、/api/logs/frontend 全部补鉴权；settings GET 返回的 apiKey 一律掩码（已有 ******** 语义，扩展成统一 maskSecret()）。
  2. matcher 纳入 /api/admin/:path*，并把 middleware 的 fail-open 改成 fail-closed（catch 后重定向登录，不是 next()）。
  3. 启动时强校验 NEXTAUTH_SECRET，缺失/为示例值即拒绝启动（当前 docker-compose 里就是 your_secret_key）。
  4. 默认管理员密码改成随机生成并打印到首次日志，或强制首次登录改密；seed 只在用户不存在时建号。
  5. SSRF 防护：对 baseUrl 做协议白名单 + 内网段/元数据地址黑名单。
  6. 补 error-items/[id]/notes 的 userId 归属校验；注册/登录接口加 IP 限流。

P1 · 把"半成品"补成闭环

  1. 落地间隔复习：把 scheduler.ts 接进创建错题的流程，做"今日待复习"队列 + 到期提醒 + 复习结果回写 isCorrect——这是错题本相对拍照搜题的唯一护城河，优先级高于任何新 AI 功能。
  2. PracticeRecord 增加 errorItemId 外键，让练习数据能回流到具体错题。
  3. 统一鉴权抽象 getCurrentUser(req) 替换十余处样板代码，从根上消灭 IDOR 遗漏。
  4. 拆 settings-dialog.tsx（1544 行 → 按 Tab 拆 6 个子组件 + 一个 form schema）。
  5. ErrorItem 加 @@index([userId])、@@index([subjectId])；标签递归改成一次性取回后内存建树；SQLite 开 WAL + busy_timeout；备份换 .backup。

P2 · 体验与长期演进

  1. 补 Ctrl+V 剪贴板粘贴上传（桌面端刚需）；一次分析一整页试卷并自动切分成多道错题，而不是整页存一条。
  2. 把 OpenClaw 批量接口、导入导出、GeoGebra 写进 README——目前属于"代码里有、文档里没有"。
  3. 图片从"base64 存 DB"改为落 data/uploads 存路径 + 鉴权后签名访问，避免 DB 膨胀与备份困难。
  4. 测试升级：integration 用真实 SQLite 临时库跑（Prisma 完全支持），e2e 保留一条不 mock 的 AI 链路（可用固定 fixture + 便宜模型），CI 加 lint 与 npm audit。
  5. 升级 next-auth → Auth.js v5，清理版本不匹配的 Prisma adapter 依赖。
  6. 清理迁移历史（rebase 成线性）、删除 knowledgePoints 双轨、删除死代码 scheduler.ts 或直接用起来。

6. 总体评价

产品层面 8/10。需求抓得极准——家长/学生的真实痛点是"整理错题太费时间"，而它把 AI 放在"录入"这个最耗时的环节上，而不是做一个花哨的 AI 家教。标签收敛策略、上下文感知 prompt、人工校对位这几处设计明显是想过、踩过坑的，比大多数同类开源项目老练。加上 Docker/PWA/HTTPS/代理/多模型兼容这套自托管友好度，449 stars 是实打实用出来的。

工程层面 6/10。骨架（统一 AI 抽象、结构化日志、错误码、CI）搭得不错，但鉴权这块是最大的系统性缺陷：中间件把 /api/** 整体排除在外，又靠人工在每个 route 里自查，漏三个只是时间问题。这不是能力问题，是缺少"默认拒绝"的机制设计。

最大的战略缺口是间隔复习没做。错题本的价值不在于"存"，在于"在快要忘的时候再出现一次"。ReviewSchedule 表和艾宾浩斯算法都写好了却没接进主流程，等于把产品的复购理由（让孩子每天回来用一次）让给了别人。如果只做一件事，建议做这个。

适用建议：家庭 NAS / 局域网自用完全够用，功能完整度超出预期；但请勿直接端口映射到公网——先完成 P0 的六条安全修复。若作为二次开发基座，建议优先重构鉴权层与数据层索引，再叠加业务功能。
